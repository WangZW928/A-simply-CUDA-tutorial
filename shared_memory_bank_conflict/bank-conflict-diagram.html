2. Stride=1 vs Stride=32：同一个 kernel，天壤之别

✦ Stride = 1 无冲突

32 threads → 32 different banks → parallel

T0→ B0smem[0]
T1→ B1smem[1]
T2→ B2smem[2]
⋯
T30→ B30smem[30]
T31→ B31smem[31]
每个 bank 被几个线程访问 1
完成 32 次 load 需要 1 cycle ✓
执行时间线：
T0..31 ✓

✦ Stride = 32 全冲突

32 threads → same bank → 32× serialized

T0→ B0smem[0]
T1→ B0smem[32]
T2→ B0smem[64]
⋯
T30→ B0smem[960]
T31→ B0smem[992]
每个 bank 被几个线程访问 32（全堆在 B0）
完成 32 次 load 需要 32 cycles ✗
执行时间线：
T0
T1
T2
⋯
T31
3. 冲突度公式
thread_addr = lane_id × stride
bank_id = thread_addr % 32
conflict_degree = gcd(stride, 32)
stride=1 → gcd(1,32)=1 无冲突
stride=2 → gcd(2,32)=2 2-way 冲突
stride=4 → gcd(4,32)=4 4-way 冲突
stride=32 → gcd(32,32)=32 全冲突
stride=3 → gcd(3,32)=1 无冲突 ✦

关键洞察：stride=3 虽然跳跃访问，但因为 3 和 32 互质，每个线程仍然落到不同的 bank。 这就是为什么 bank_id = (lane × stride) % 32 比直觉更微妙。

4. 为什么这个实验必须用 volatile？
❌ 不用 volatile（编译器优化后）
// 原始代码
acc += smem[index];

// 编译器识别出 smem[index] 在循环中不变
// → 把 load 提升到循环外：
float tmp = smem[index];
for (...) acc += tmp; // 全是寄存器操作

→ 测到的不是 bank conflict，
是寄存器加法速度
✅ 用 volatile（真实测量）
// 修正代码
volatile float* vsmem = smem;
acc += vsmem[index];

// volatile 告诉编译器：
// "每次循环都必须重新从内存读取"
// 不允许提升、不允许缓存

→ 每次迭代真的走 shared memory
→ bank conflict 现象被观测到

一句话总结
Shared memory 是 32 条"通道"（bank），每个 cycle 每条通道只能过一个人。 如果 32 个线程各走各的通道 → 并行通过。 如果全挤一条通道 → 排队 32 次。
而 volatile 的角色是：不让编译器偷偷把"走路"换成"抄答案"。
